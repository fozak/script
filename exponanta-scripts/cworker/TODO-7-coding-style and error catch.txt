The actual, narrow reasons you’d want a class instead of the function here:

instanceof CWError specifically (not just instanceof Error) — if you ever want catch (err) { if (err instanceof CWError) ... else ... } to distinguish “an error we deliberately threw with code/status” from “some unrelated JS exception that leaked through” (a TypeError from a bug, say). The function-built version is only ever instanceof Error — never distinguishable from any other plain Error by type, only by duck-typing ('code' in err).
A family of subclasses (BadRequestError extends CWError, ForbiddenError extends CWError) — if later you want catch (err) { if (err instanceof ForbiddenError) ... } branching by kind, not just by string code. A function has no equivalent — you’d be back to checking err.code === "..." strings everywhere, which is exactly the inconsistency problem we’re trying to get away from.
Clean subclass construction with super(message) keeps the stack trace pointing at the throw site correctly, same as the plain function’s new Error(message) does — no actual difference here, confirmed.

So, honestly: for what you’re doing right now — one error shape, carrying code+status, caught once in CW.controller — the plain function is equally correct and slightly simpler. The class only earns its keep if you expect to later need instanceof-based branching by error kind, not just reading err.code. Given this codebase doesn’t do that kind of branching anywhere yet, the function is the more honest, minimal choice — I over-reached calling the class “the” canonical answer.

function cwError(message, { code, status = 400 } = {}) {
  const err = new Error(message);
  err.code = code;
  err.status = status;
  return err;
}
