Unverified: {

    allow:   (run_doc) => boolean,        // self-storing

    }
  }
}

allow is a function that stores its own result. cascade is a map of dotpath pointers — runner resolves each dotpath against the doc, finds the adapter name, calls Adapter[name][key](run_doc), stores the result. Clean, symmetric, complete.

Key things from prior discussions that affect what we just concluded:

1. next was already established as redundant earlier
From the prior session — next was a router returning a signal string post-DB-write. But we just proved the branch structure itself encodes from.to. This confirms next removal is correct and consistent with the earlier signal format dim.From.To.

2. cascade keyword in dot path was already resolved
Prior session established:

status.Unverified.Active.inform   ← correct
status.Unverified.Active.cascade.inform  ← redundant, removed
So our current cascade: { inform: ..., token: ... } is correct in schema but the runtime dot path skips the word cascade.

3. Signal format was dim.From.To not dim.From_To
Prior session used "status.Invited.Unverified" dot notation — matches what we landed on today. Consistent.

4. One edge we missed today — allow writes to input
From prior session:

js
allow: (run_doc) => {
  run_doc.input._allow = boolean  // writes result to input
}
But today we made allow a pure boolean return. These are inconsistent. The prior session had allow mutating input so the pipeline could carry the result. Today's version returns a boolean directly to the runner.

The boolean return is cleaner — the runner reads it directly without needing input._allow. But it's a change from the prior established pattern worth noting.

5. inform key naming
Prior session used named cascade functions like SendVerificationUser registered in CW.sideEffects. Today we replaced that entirely with inform: { send: "settings.default.inform" }. This is a breaking change from the prior convention — but the correct one given the adapter architecture we established today.
